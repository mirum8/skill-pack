2 · Problem, goals & non-goals

Who hurts, and how much

Fifteen skills and eight agents currently live as loose directories in ~/.claude/skills/ and ~/.claude/agents/ on one machine. They are not version-controlled as a unit, they cannot be installed anywhere else without copying directories by hand, and their names follow three different conventions at once — verb-first (write-tests, find-bugs), noun-first (claudemd-compact, local-scan), and bare verbs (commit, refactor). Nothing distinguishes them in the / menu from the twenty-odd unrelated skills sitting beside them.

The concrete costs today: a second machine gets none of them; a rename means hand-editing cross-references with no way to find them all; and there is no artefact that says which skills depend on which, so removing one is guesswork. The dependency graph is real and dense — post-task-review alone references local-scan 22 times.

3 · Business domain

Narrative

An agent skill is a markdown file of instructions that an LLM coding agent loads on demand. Claude Code discovers skills from directories, keeps only each skill's short description permanently in context, and loads the full body only when the skill is invoked — by the user typing /name, or by the model deciding the description matches the task. That last point is what makes this domain unusual: the product's routing layer is a language model reading prose. A skill with a vague description is not a documentation problem, it is a dispatch failure.

Nobody pays anybody here. The economics are context and attention: every description costs tokens in every session forever, while every skill body costs nothing until used. That asymmetry is the whole design pressure — descriptions must be short enough to afford and specific enough to route correctly, and bodies can be as long as they need to be. A pack of fifteen skills is therefore a shared budget problem, not fifteen independent files.

What the maintainer actually does all day: invokes these skills against real repositories, notices one mis-fires or goes stale, edits the markdown, and wants the edit to apply immediately and to exist on every machine. The risk sits in silent failure — a skill that stops triggering, or triggers instead of a better one, produces no error. It just quietly does not happen.

4 · Prior art

Problem framing

The category is agent skill distribution — packaging prompt-and-instruction assets so an agent runtime discovers them, with versioning and an install path. It is adjacent to editor-extension packaging and to dotfile management, and it borrows from both: a manifest and a namespace from the former, clone-in-place and live editing from the latter. Claude Code skills follow the Agent Skills open standard [verified: code.claude.com/docs/en/skills, read 2026-07-30], so the format is portable even though the packaging mechanism here is Claude-Code-specific.

Must-have gates

  1. Produces a real namespace prefix, so the skills are visually separable in the / menu. Non-negotiable: this is the user's stated requirement.
  2. No marketplace publication and no submission to any central catalogue.
  3. Install is one command on a fresh machine.
  4. Editing a packed SKILL.md affects the current session, because the maintainer edits these daily.
  5. Carries agents and executable scripts, not markdown alone — the pack includes .workflow.js, Python and shell.

5 · Requirements

Functional

FR-1 must — The pack shall contain .claude-plugin/plugin.json with "name": "r" at the repository root, so that the repo is discovered as a skills-directory plugin when reached from a skills directory.

Given the repo cloned to a working directory of the maintainer's choosing and copied into ~/.claude/skills/r by install.sh, when a new session starts, then /plugin lists r@skills-dir and /r:git-commit resolves.

The install copies rather than symlinks, and that is what makes this requirement ordinary rather than risky. A <skill-name> entry at the personal location "can be a symlink to a directory elsewhere on disk. Claude Code follows the symlink and reads SKILL.md from the target directory" [verified: skills docs, read 2026-07-30] — but nothing states that @skills-dir plugin discovery follows a symlinked entry to find .claude-plugin/plugin.json, and the marketplace symlink rules do not apply, because a skills-directory plugin is "discovered in place rather than copied into the plugin cache" [verified: plugins-reference, read 2026-07-30]. A real directory holding the manifest is the documented case and needs no such assumption. The cost moves to ADR-11's consequence — two copies, and a publish step.

FR-2 must — The pack shall place all fifteen skills as immediate children of skills/, each independently invocable.

Given the pack is discovered, when the user types /r:, then all fifteen names appear in autocomplete and any one can be invoked without invoking another.

FR-3 must — Each skill directory shall be named per BR-1, following the rename map in BR-2.

Given the rename map, when the pack is built, then every directory under skills/ matches ^[a-z0-9]+(-[a-z0-9]+){0,2}$ and equals its map target.

FR-4 must — When a skill body contains a reference to a renamed skill, the build shall rewrite it to the r:-prefixed new name, and shall leave every non-reference occurrence byte-identical.

Given 678 raw occurrences of old names of which 309 are references, when the rewrite runs, then exactly 309 occurrences change and a diff of the remaining 369 is empty.

FR-5 must — The pack shall ship an agents/ directory containing the eight agents that packed skills dispatch.

Given a fresh machine with only the pack installed, when /r:task-review dispatches bug-hunter-ui, then the agent resolves rather than failing as unknown.

FR-6 must — The pack shall provide an install script that clones or updates the repo, copies its payload into ~/.claude/skills/r overwriting what is there, provisions the mandatory prerequisites of FR-21, removes the superseded global guard registration per FR-20, and reports the next required action.

Given a machine with git and Claude Code, when the script runs on a clean machine, then the repo is present at its working location, ~/.claude/skills/r holds a copy of the payload, every mandatory prerequisite reports present, and the script prints that a session restart is required; when it runs over an existing install, then it overwrites and prints that /reload-plugins is required for non-SKILL.md changes.

Only the payload is copied — .claude-plugin/, skills/, agents/, hooks/ and check-prereqs.sh. docs/, tools/, validate.sh and .git/ stay in the repo: the install needs what Claude Code loads and nothing else.

Because the copy deletes anything at the destination that the repo does not have, the script shall refuse to run when ~/.claude/skills/r exists and is not a previous install of this pack — a wrong CLAUDE_SKILLS_DIR, or a directory that happens to share the name, must not be silently erased.

The script no longer merely clones and prints — FR-21 makes it run package-manager commands, which is a deliberate reversal of an earlier control and is carried as R-12.

FR-7 must — Every SKILL.md frontmatter block shall parse under a strict YAML parser.

Given spec-to-todo's current unquoted description containing Stack-agnostic: it follows…, when it is converted to a >- block scalar, then yaml.safe_load succeeds for all fifteen.

FR-8 must — If a skill's description plus its when_to_use exceeds 1,536 characters, then the build shall fail rather than ship a silently truncated description.

Given run-task's 2,174-character description, when the build runs before it is rewritten, then the build fails naming the skill and the overage (638). Given a skill that later adds when_to_use, then the check counts both fields together, because when_to_use is "appended to description in the skill listing and counts toward the 1,536-character cap" [verified: skills docs, read 2026-07-30]. No skill uses that field today, which is why the measured 15,186 total is still correct.

FR-9 must — The pack shall contain no dangling references: every skill name referenced in a body is packed, bundled with Claude Code, or listed as an external prerequisite in the README.

Given the reference inventory, when the check runs, then it reports zero unclassified names; /security-review and /simplify classify as bundled, codex:adversarial-review and agent-browser as documented external.

FR-10 must — The pack shall drop version: from every SKILL.md.

Given the four skills carrying version:, when the pack is built, then no SKILL.md contains version: and the pack version lives in plugin.json plus a git tag. No longer conditional: version is absent from the documented frontmatter field list, and unlike plugin.json the skills documentation carries no "unrecognized fields are ignored" clause — so it is an undocumented key of unknown effect [verified: skills docs, read 2026-07-30].

FR-11 must — The pack shall carry a real eval suite for every one of the fifteen skills under skills/<name>/evals/.

Given only git-commit and spec-brainstorm have evals.json today, when the pack ships, then those two are carried over unchanged and thirteen new suites exist, each asserting at least that the skill triggers on its intended phrasing and does not trigger on its nearest neighbour's. Placeholder or empty files do not satisfy this.

This is the one addition promoted into v1, and it is what turns the "not instrumented" rows in §13 into measurable ones: evals are the only mechanism that catches a description drifting until it stops triggering.

FR-12 should — Where third-party material is vendored, the pack shall preserve its LICENSE verbatim and record provenance and retrieval date in the README.

Given the 380 KB html-effectiveness tree, when the pack ships, then its LICENSE, CODE_OF_CONDUCT.md and SECURITY.md are intact and the README names its origin.

FR-13 must — The pack shall exclude build artefacts from version control.

Given two committed __pycache__/*.pyc files under post-task-review/scripts/, when .gitignore is applied, then git status --porcelain --ignored shows them ignored and no .pyc is tracked.

FR-14 must [amended 2026-07-31] — Before the fifteen flat originals are deleted, the pack shall be installed and every one of the fifteen shall resolve under its /r: name, and the originals shall be archived to a verified backup. Until then they shall remain installed and functional under their old names.

This requirement originally said permanently, with no cut-over and no deletion step (ADR-13). The user reversed that on 2026-07-31 once the pack was installed and proven, so what the requirement now states is the precondition the cut-over actually had to meet — which is the part that was load-bearing.

The dual-run did its job before it ended. It is what made the cut-over safe to do at all: the pack ran alongside the originals until /plugin listed r@skills-dir, all fifteen resolved, and the fifteen-versus-fifteen comparison could be made on a live machine rather than argued about.

Given the originals deleted, when the user types /commit, then nothing resolves; when they type /r:git-commit, then the packed skill runs. The requirement that survives is the one that always mattered: only the packed copy is ever edited — now trivially true, because there is no other copy. R-4 is closed by the same act, and FR-17's drift check reports it closed rather than failing once per missing file.

What the reversal costs is the rollback this requirement existed to provide. Falling back to an old name is no longer free: it means restoring from ~/.claude-backups/. That is a real archive, verified by extracting it and diffing against the live tree before anything was deleted, but it is a restore step where there used to be none.

FR-15 must — The pack shall ship a single check-prereqs.sh that reports every external prerequisite as mandatory or optional, and shall exit non-zero only when a mandatory one is missing.

Given a machine, when the script runs, then it reports each of pmd, spotbugs, semgrep, python3, node and agent-browser as mandatory, and gh (present and authenticated) and the codex plugin as optional; and it prints the install command for anything missing. Given only the codex plugin missing, or only gh, then it warns and exits zero.

gh is optional because GitHub is one source among several, not the floor: task-run also runs from a todo phase, a list item or free text and finishes by merging the feature branch, and issues-fix falls back to the list file at the repo root. Its absence costs issue sources, gh pr create and issue-closing — named, in the script's own output and again at the point of use, never worked around. Authentication sits at the same tier rather than a stricter one, because gh present but logged out reaches exactly as far as gh absent.

This requirement was rewritten, and the reason matters more than the text. It previously demanded per-skill prerequisite checking that already exists upstream and is better than an install-time check, because it fires at the moment of need with the context to say what is uncovered: code-scan ships scripts/check-tools.sh, which names each analyzer, prints its brew line, runs on a subset while telling the user which categories are therefore uncovered, and exits 1 when none is available [verified: local-scan/scripts/check-tools.sh, read 2026-07-30]; gh-issues-fix gates the whole loop on command -v gh && gh auth status [verified: fix-gh-issues/SKILL.md:53]; and code-adversarial's wrapper exits 3 when the Codex companion is absent [verified: adversarial-review/scripts/run.sh:54]. So this requirement documents and aggregates those guards rather than replacing them. What it genuinely adds is the one question they cannot answer between them — "will this pack work on my machine at all?" — asked once, before the first failure.

Promoted into v1, with agent-browser the only prerequisite that had no guard of any kind.

FR-16 must — Where a skill's own text states it must not fire on its own, the pack shall set disable-model-invocation: true on it, so the stated rule is enforced by the harness rather than by hope.

Given post-task-review, whose body says "This routine is NOT automatic… Never trigger it on your own", when it is packed as task-review, then its frontmatter carries disable-model-invocation: true and the model cannot auto-load it. Same for task-run and gh-issues-fix.

FR-17 must — The pack shall ship a local pre-push validation script, and it shall be run before every push.

Given the pack, when the script runs, then it executes every static check in §12 — manifest parses with name == "r", fifteen skill directories at depth two, names matching BR-1 and the BR-2 map, all frontmatter valid YAML, no description over cap, zero dangling references, no version: key, every bundled agent dispatched by some packed skill, no tracked *.pyc — plus the R-4 drift check comparing each flat original against its packed twin, and exits non-zero naming every failure.

This is the substance behind ADR-10: CI was declined, so the same checks exist as a script run by hand. Every check is static and completes in under a second, which is what makes declining CI survivable rather than merely cheaper.

FR-18 should [deferred to v2] — The pack shall enforce in frontmatter what two skills currently only assert in prose: paths to stop JVM-only skills auto-firing on unrelated work, and disallowed-tools to make report-only skills genuinely unable to edit.

Given tests-write and code-scan, which apply only to .java and .kt sources, when they carry paths globs for **/*.java and **/*.kt, then Claude "loads the skill automatically only when working with files matching the patterns" [verified: skills docs, read 2026-07-30]. Given code-bugs and code-quality, whose own text says they never edit, when they carry disallowed-tools: Edit Write, then those tools are removed from the pool while the skill is active and the promise becomes structural rather than advisory.

Deferred because it changes behaviour, which ADR-12 keeps out of the rename diff. The cost of deferring is R-9.

FR-19 must — The pack shall carry no absolute path to a skill directory. Every such reference shall resolve through a substituted variable instead.

Given the 42 hard-coded references measured across twelve files in seven skills, when the pack is built, then each of the 26 self-references uses ${CLAUDE_SKILL_DIR} and each of the 16 cross-skill references uses ${CLAUDE_PLUGIN_ROOT}/skills/<new-name>/…; and grep -rE '(\$HOME|~)"?/\.claude/skills/' over the pack returns only the two intentional originals inside the guard's CANON (FR-20).

FR-20 must — The pack shall ship the workflow-immutability guard as its own PreToolUse hook, declared in hooks/hooks.json at the plugin root, and its allow-list shall be built at run time from $CLAUDE_PLUGIN_ROOT plus the two flat original paths.

Hooks may live either in "hooks/hooks.json in plugin root, or inline in plugin.json" [verified: plugins-reference, read 2026-07-30]. The separate file is chosen so plugin.json stays what R-5 calls the single point of failure — identity and namespace only — rather than also carrying executable wiring whose syntax errors would take the whole namespace down with them. Note the documented trap: hooks/ belongs at the plugin root, never inside .claude-plugin/, which holds nothing but the manifest.

Given the guard's current allow-list is the literal pair ~/.claude/skills/post-task-review/post-task-review.workflow.js and ~/.claude/skills/run-task/run-task-implement.workflow.js, and given its PTR regex blocks any Workflow call whose script declares meta.name of post-task-review or run-task-implement from any other path, when the packed copies run from ${CLAUDE_PLUGIN_ROOT}/skills/task-review/…, then they are permitted; and when a genuine fork is attempted from anywhere, then it is still blocked.

Because the install copies (ADR-11), $CLAUDE_PLUGIN_ROOT is already a real directory and needs no special handling. The guard's existing os.path.realpath() calls on both the allow-list entries and the incoming scriptPath remain correct either way.

The install script shall remove the superseded global registration at ~/.claude/settings.json, because a guard registered outside the pack would keep blocking the packed copies no matter what the packed guard permits.

The packed guard shall additionally narrow its match to files that are actually workflow scripts, rather than any file whose text contains a guarded pipeline name. This was observed, not predicted: while this specification was being written, the guard blocked an edit to interview-notes.md — a prose document, in an unrelated repository, that merely quoted the two guarded names in their declared form. The consequence is concrete and self-inflicted if left unfixed: the pack's own README, spec and notes could not describe the pipelines they ship, and neither could the rename script of FR-4, which must write those very strings while rewriting references. A guard that blocks documentation of the thing it protects is over-matching, not protecting.

FR-21 must — The install script shall provision every mandatory prerequisite, printing each command before running it, and shall support --dry-run and --no-deps.

Given a machine missing the analyzers, when the script runs, then it executes brew install pmd spotbugs semgrep and npm i -g agent-browser && agent-browser install, each echoed first; and when run with --dry-run, then it prints the same commands and executes none.

Mandatory because the pack's own pipeline depends on them: code-scan is invoked 22 times by task-review, and agent-browser is reached through task-review → bug-hunter-ui → /test-app, where the generated skill calls UI verification "Mandatory whenever UI is in scope" [verified: create-test-app/assets/test-app.SKILL.md.template:86].

--no-deps exists because this step couples install to Homebrew and therefore to macOS (R-12); it is the escape hatch for any machine that provisions differently.

FR-22 must — If the codex plugin is absent, then the affected step shall be recorded as skipped and the run shall continue; and it shall never be satisfied by a model-written substitute.

Given a machine without the Codex plugin, when /r:code-adversarial runs, then it reports the review as not run, names the missing plugin and how to add it, and returns a skipped result rather than stopping the caller; and when /r:task-review runs, then its report shows the Codex step as skipped and every other step as executed.

Skipped must never decay into faked. The prohibition in adversarial-review's own text — "Do not fake a review or substitute an LLM imitation" [verified: adversarial-review/SKILL.md:83] — survives this requirement verbatim. A skipped step that is reported as skipped is honest degradation; a skipped step reported as a review is the single failure that would make the whole pipeline worthless, and it is the reason this requirement specifies the report and not just the control flow.

This is a behaviour change, not a repackaging change: it reverses today's exit-3 stop, and task-review's two encodings — the workflow script and references/prose-pipeline.md — must change together or the two engines silently diverge. That places it against ADR-12 and ADR-14, which keep behaviour changes out of the rename diff. Carried as R-11.

Retention and classification

No personal data, no secrets, no user content — the pack is instructions. 9 · Security & error handling

Trust and blast radius

A skill is arbitrary instructions to an agent with tool access, and this pack additionally ships executable Python, shell and JavaScript. Installing it at personal scope means no trust gate at all — personal-scope plugins have none of the project-scope restrictions [verified: plugins-reference, read 2026-07-30]. That is the right trade-off for the author's own machine and the wrong one for anybody else, so the README must say so plainly rather than presenting the pack as generally installable.

11 · Runtime flows

Five flows matter. The first is drawn because it is the one that must work; the rest are step lists, including three failure paths.

Flow 1 — fresh install to first invocation (happy path)

Flow 2 — edit a skill (happy path)

  1. Maintainer edits ~/.claude/skills/r/skills/git-commit/SKILL.md.
  2. The change is live in the current session immediately — no reload, no restart.
  3. If instead they edited agents/bug-hunter-ui.md, hooks/ or .mcp.json, nothing happens until /reload-plugins.
  4. git commit and git push; other machines pick it up on their next ./install.sh.

Live-edit and reload behaviour: [verified: code.claude.com/docs/en/plugins-reference, read 2026-07-30].

Flow 3 — the pack fails to load (failure path)

  1. A trailing comma is introduced into plugin.json.
  2. Next session start: the loader finds no valid manifest, so the folder is treated as a plain skill directory rather than a plugin.
  3. Every /r: command silently ceases to exist. There is no error, no warning, and autocomplete simply offers nothing.
  4. Detection: /plugin does not list r@skills-dir. This is the only reliable signal.
  5. Recovery: fix the JSON, restart. With ADR-10 there is no automated gate to stop step 1 reaching main — see R-5.

Flow 4 — a review step silently does not run (failure path)

  1. /r:task-review reaches its Codex adversarial step.
  2. The machine has no codex plugin, so codex:adversarial-review does not resolve.
  3. Without FR-15: the step is skipped or improvised, and the run reports a completed review that never happened — the worst failure in this system, because the output looks identical to success.
  4. With FR-15: the skill checks first, stops, and names the missing plugin and the command to add it.

Flow 5 — the rename corrupts prose (failure path)

  1. A build script runs sed -i 's/commit/git-commit/g' across the pack.
  2. All 101 occurrences of commit change, but only 2 were references. Ninety-nine English sentences now read "create a git-commit".
  3. Nothing fails. Tests pass, the pack loads, and the instructions are subtly wrong forever.
  4. Prevention: BR-3's four bounded patterns, and NFR-5's diff-count check against the 369 expected-unchanged occurrences.

Reconciliation — permanent, not a phase

Both copies exist forever, so they can diverge forever. The reconciliation rule is one-directional and absolute: the pack is the only place edits are made. An edit that lands in a flat original by habit is not lost at a cut-over — there is no cut-over — it simply sits there, working when you type the old name and missing when you type the new one, which is harder to notice than losing it outright.

That is why the drift check in FR-17 is not optional housekeeping but the only control on R-4: it diffs each original against its packed twin and expects differences only in the name and its references. Any other difference is an edit that went to the wrong copy, and the script says which file.

Human review path

Every skill in the pack is user-invocable, so the human override is always available: type the name and the model's routing choice is bypassed entirely. Three skills go further and are barred from auto-firing altogether (FR-16). There is no case where the model's choice cannot be overridden, which is what keeps mis-routing an annoyance rather than a hazard.

Monitoring for drift

Drift here means descriptions slowly overlapping until routing becomes unreliable — likely as the pack grows, and invisible while it happens. This is monitored in v1, because FR-11 requires an eval suite for all fifteen skills and each asserts both that its skill triggers on its own phrasing and that it does not trigger on its nearest neighbour's. A suite that starts failing is drift, caught the next time the suites run rather than the next time a review silently goes to the wrong skill.

One cheap static check belongs alongside them in FR-17: flag any two descriptions whose leading sentence shares most of its significant words. With every packed skill's flat twin also in the listing (ADR-13), exact-duplicate descriptions are guaranteed rather than hypothetical, so the check must compare across the pack only and treat each pack/original pair as expected.
